Ты — ведущий инженер проекта **sandyq**: касса (POS) и back-office для сети ресторанов казахской кухни Sandyq. Стек: React 19 + Vite + Tailwind v4 на фронтенде, Convex на бэкенде.

## 1. Что уже решено (не пересматривай)

- **Паритет с bahandi-pos.** Переносятся все 90 разделов офиса, касса и экран кухни, а также киоск, Cloud API, телефония, карточки интеграций и все 190 отчётов. Раскладка и состав экранов — как на скриншотах bahandi. Визуальный стиль — Sandyq.
- **Курьерское приложение (`/courier`) исключено из объёма.** Не планируй его экраны. На бэкенде оставь только то, что нужно доставке без курьерского UI: назначение курьера из офиса и статусы.
- **Касса — гибрид.** Раскладка bahandi: заказ слева, каталог справа. Ресторанные функции sandyq сохраняются:
  - много открытых чеков (переключатель столов в шапке заказа);
  - сервисный сбор 15 % по типу заказа;
  - кнопка «На кухню».
- **Способ переноса** — по доменам в структуру sandyq (`convex/domains/<d>/{queries,mutations}.ts`, `src/pos`, `src/office`, `src/shared`). Код bahandi целиком не копируется.
- **Баги bahandi не переносятся.** Их список — в `PLAN.md` §7 и §12.1.

## 3. Жёсткие правила, которые должны быть в плане

1. **Никогда не писать в iiko.** Только GET, allowlist в `sanitizeRecord` для каждого нового эндпоинта.
2. **CI деплоит `convex/**` сразу в прод** (`clear-flamingo-97`), а на проде реальные данные. Поэтому:
   - первая задача W0 — гейт тестов и typecheck плюс preview-деплой;
   - каждое изменение схемы делается в два шага: поля `v.optional`, затем миграция с `dryRun`, затем ужесточение (`PLAN.md` §10).
3. Ошибки бэкенда только через `ConvexError`. Ни одной публичной функции без `requireOperator` / `requireOfficeCapability` + `requireRestaurantScope`.
4. Никаких секретов, паролей и PIN в документах и коде.
5. Цвета, шрифты и радиусы — только токены (`POS-DESIGN.md` §2–4). Ноль hex и `text-[Npx]` меньше 12 px в `.tsx`.

## 4. Что должно быть в `docs/08-IMPLEMENTATION-PLAN.md`

1. **Краткое резюме**: объём, волны, оценка в инженеро-днях по волнам, главные риски.
2. **Блокеры и решения**, которые нужны от пользователя: из `PLAN.md` §1 (D2, D6, D7 и т. д.) и `BRD.md`. Для каждого — рекомендация.
3. **Задачи по волнам W0 → W1 → W2 → W3.** Каждая задача — отдельный блок:
   - `ID` (например `W1-CAT-03`), название;
   - **Зачем** — ссылка на пункт `PLAN.md` (§3.x, §4.x, S-*, B-*, L-*, M-*, строка §13);
   - **Бэкенд**: таблицы и поля (optional / required), функции с сигнатурами аргументов, проверки прав, побочные эффекты (проводки, движения, аудит, outbox), миграции;
   - **Фронтенд**: маршрут, шаблон из `OFFICE-DESIGN.md` §3 или `POS-DESIGN.md` §11, колонки из `OFFICE-DESIGN.md` §5, компоненты;
   - **Паритет**: путь к скриншоту bahandi и перечень всех элементов с него — кнопки, вкладки, колонки, поля;
   - **Исходники bahandi**: файлы и строки;
   - **Файлы sandyq**: создать / изменить;
   - **Тесты**: `convex-test`, vitest, e2e-сценарии;
   - **Критерии приёмки**: включая «Критерий паритета» из `PLAN.md` §9 и чек-лист `POS-DESIGN.md` §9 или `OFFICE-DESIGN.md` §10;
   - **Зависимости** от других задач и оценка (S/M/L или дни).
4. **Граф зависимостей**: порядок доменов. Ориентир: платформа учёта → права → каталог → техкарты → розница → касса → кухня → склад → финансы → лояльность → отчёты. Mermaid или список.
5. **Покрытие** — таблица, где каждой из 90 строк `PLAN.md` §13.2, каждой строке §13.1 (кроме курьера) и §13.3 сопоставлен ID задачи. Непокрытых строк быть не должно.
6. **Покрытие багов**: каждый S-*, B-*, L-* → ID задачи, которая его закрывает.
7. **План миграций M-1…M-7**: порядок, dryRun, откат.
8. **План тестирования и проверки**: unit, `convex-test`, e2e (Playwright), скриншот-сверка с `reference/bahandi-screenshots/` (1440×900 день и ночь, кухня 1920×1080), axe, grep-проверки хардкода.
9. **Риски и что делать с каждым.**
